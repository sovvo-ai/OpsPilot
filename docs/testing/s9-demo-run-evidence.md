### 2:20 澄清 —— 零模型调用的硬否决

```
信息不足，我需要再确认一下才能回答。

请补充以下任一信息：
1. **具体服务/组件名**（如 Nginx、MySQL、某个 Pod），以及它的报错原文；
2. **错误日志片段**（含时间戳与 error 行），我可以直接分析；
3. **端口号与现象**（如「8080 起不来」「3306 连接被拒」），便于判断是否端口冲突。

你指的是哪一种？
```

### 1:30 排障回答 —— 工具证据与 KB 证据分开标

```
未在知识库找到与日志内容直接相关的依据。
工具分析指出错误类型为 `connection_refused`，对应 `ERROR` 级别日志，关键行为发生在第 1–3 行[工具]。

根据知识库规范：
- `ERROR` 级别日志仅用于需人工介入的失败，例如依赖不可用[1]；
- `connection_refused` 通常表明上游服务未监听目标端口或已崩溃，属典型依赖不可用场景。

建议优先排查：…

（模型通用知识，无 KB 出处）
```

> `[工具]` 标工具结论、`[n]` 标 KB 片段、显式标注「模型通用知识，无 KB 出处」—— 三类证据边界清晰。

## 本轮实跑修出的**脚本缺陷**（不是产品缺陷，如实记录）

| # | 现象 | 根因 |
|---|---|---|
| 1 | 2:20 澄清段抓到的是**排障回答** | 脚本**未清除上一段的 `attach_log`** —— 带日志提问按 D1 语义**正确地**走了排障。修：切会话前调「清除」。 |
| 2 | 2:20 助手消息**内容为空** | 澄清路径**零 delta 事件**，`wait_stream_done`（判 `.cursor` 消失）返回过早，前端 `finally` 重渲染尚未落地。修：改为等「信息不足」文案出现。 |
| 3 | 后续段截图**带着上一段的抽屉** | 段间未关抽屉。修：切段前显式关闭。 |

> 这三处都属**存证脚本的状态管理**问题 —— 产品行为是对的（甚至 #1 反过来验证了 D1 语义）。
