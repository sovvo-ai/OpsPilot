## 2. FB1 · 诱饵集越界流出

### 2.1 测量设置

| 项 | 值 |
|---|---|
| 数据 | `ai-service/evals/datasets/critic_golden.jsonl`（**8 题**） |
| 轮次 | **3 轮**，on/off 各跑（每轮 8 题 × 2 臂） |
| 检出器 | `detect_citation_overreach`（机器口径，只扫含 `[n]` 的句子） |
| 判定 | **3 轮均值**（delta PRD §2.2 要求，单次只能算点估计） |

### 2.2 逐轮原始数据（**不许只报均值**）

| 轮次 | 基线（off） | filter（on） |
|---|---|---|
| 第 1 轮 | **8** 处 | **0** 处 |
| 第 2 轮 | **7** 处 | **1** 处 |
| 第 3 轮 | **9** 处 | **1** 处 |
| **均值** | **8.00** | **0.67** |
| **目标（基线 10%）** | — | **≤ 0.80** |

**降幅 = (8.00 − 0.67) / 8.00 = 91.6%**

### 2.3 逐题明细（filter 臂第 1 轮，含审计字段）

| 题 | route | overreach | 引用数 | 保留 chunk | **剔除 chunk** | 锚点数 |
|---|---|---|---|---|---|---|
| b001 | kb_qa | 0 | 1 | 1 | **4** | 2 |
| b002 | kb_qa | 0 | 1 | 1 | **4** | 9 |
| b003 | kb_qa | 0 | 1 | 1 | **4** | 9 |
| b004 | kb_qa | 0 | 1 | 2 | **3** | 2 |
| b005 | kb_qa | 0 | 2 | 2 | **3** | 1 |
| b006 | troubleshooting | 0 | 3 | 4 | **1** | 7 |
| b007 | kb_qa | 0 | 2 | 2 | **3** | 5 |
| b008 | kb_qa | 0 | 1 | 2 | **3** | 4 |

> **这张表是本报告最重要的证据**：`剔除 chunk` 列有值，说明**过滤真的在节点内跑了**。
> 首轮评测曾出现"越界降了但剔除数为 0"的矛盾，根因是评测脚本重复接线（见 §6）。

### 2.4 基线为什么是 8.0 而不是 SPike 的 21

SPIKE 的 21 处是**主集 3 题 × 5 轮**（含 `m001` 多轮形态，单题一次能出 3 处）；
本次是**诱饵集 8 题 × 1 轮**。**基数不同，不可直接比较**。
本报告只做**同次对照**（同一题集 on/off），这是 delta PRD §2.2 的口径要求。

## 3. FB2 · 主集检索指标

### 3.1 测量设置

| 项 | 值 |
|---|---|
| 数据 | `qa_golden.jsonl` 35 题（**主集基线不动**） |
| 口径 | `gold_chunk_texts` 子串匹配（与 `run_eval.py` 同源） |
| 方式 | 只跑检索，不跑生成（排除生成随机性干扰） |

### 3.2 结果

| 指标 | filter off | filter on | Δ | 判定 |
|---|---|---|---|---|
| **Recall@5** | 0.9259 | **0.9259** | **0.0000** | ✅ 严格相等 |
| **MRR@5** | 0.7728 | **0.8704** | **+0.0975** | ✅ 高于基线 |
| 丢失命中题 | — | **无** | — | ✅ |
| 新增命中题 | — | **无** | — | — |

**MRR 提升的原因**：污染 chunk 被剔除后，正确 chunk 在结果集中的**位置前移**。
不是巧合，是"过滤噪声 → 排名改善"的直接效果。

**丢失命中 = 0**：这是 FB2 最关键的断言 ——
过滤器把检索集从 4.44 压到 1.74（保留率 39.2%），**但没有压掉任何一个 gold 命中**。

## 4. 残留：filter 治不了的那一类（**不许隐瞒**）

### 4.1 残留事实

filter 臂 3 轮中仍有 **2 轮各 1 处**越界（`b008`）。均值 0.67，**不是 0**。

| 项 | 内容 |
|---|---|
| 现象 | filter 后仍偶发越界 |
| 形态 | **正确片段（主题对）内部不支撑该结论**时，模型仍为该结论挂该片段的 `[n]` |
| filter 为何治不了 | filter 只判"chunk 属不属于本主题"，**不判"这句话是否被该 chunk 支撑"** |
| 本迭代处置 | **接受并记录**（ADR-0002 §4 逐字存档，作为 V1.2 立项证据） |

### 4.2 对外表述底线

| 可写 | 不可写 |
|---|---|
| 「越界流出降低 91.6%（8.0→0.67，3 轮均值，同次对照）」 | ❌「引用越界已根治」 |
| 「残留 0.7/轮，形态见已知限制」 | ❌「filter 解决了引用越界问题」 |
| 「MRR +0.0975，Recall 零损失」 | ❌「检索质量全面提升」（只有 MRR 提升，Recall 是持平） |

> **「根治」二字只能出现在否定句里。**

## 5. FB3 · 延迟（配对法）

### 5.1 为什么换方法

SPIKE 的 n=15 测出 **P50 +594ms 而 P95 −1548ms** —— 方向打架。
filter 是纯字符串匹配，理论增量 ≈0，两个相反的差值只能说明**测到的是模型时延噪声**。

### 5.2 预注册方法（delta PRD §2.3）

```
30 题 × 3 轮 = 90 对，on/off 同题相邻跑（抵消账号/时段漂移）
统计：逐题配对差值的均值 ± 95% CI（bootstrap 10000 次）
达标线：均值 ≤ +500ms 且 P50/P95 方向一致
```

### 5.3 结果

| 统计量 | 值 |
|---|---|
| 有效配对数 | **90** |
| 配对差值均值 | **−219.1ms** |
| 95% CI（bootstrap 10000） | **[−746.8, +244.6]ms** |
| off P50 / P95 | 4296ms / 11921ms |
| on P50 / P95 | **3843ms** / **11109ms** |
| P50 方向 | **改善**（−453ms） |
| P95 方向 | **改善**（−812ms） |
| **判定** | ✅ **PASS** |

### 5.4 诚实解读

**CI 上界 +244.6ms 跨过 0**，说明"on 比 off 快"这个方向在统计上不稳健。
正确表述是：

> **配对差值均值 −219ms，95% CI [−747, +245]** ——
> **无法证明 filter 变快，但可以排除"显著变慢"（上界 +245ms < 500ms 阈值）。**

这与物理直觉一致：filter 是纯 CPU 字符串匹配，增量本来就该接近 0；
测试里看到的差异主要是**模型时延噪声**，不是 filter 的功劳。
**不许写"filter 提升了性能"。**

## 6. ⚠️ 首轮评测的接线缺陷（已修，必须记录）

### 6.1 现象

首轮跑完 FB1 显示：基线 8.7 → filter 0.7（看起来达标），
但逐题明细里 **`filtered_out = 0`、`filter_reason = None`** ——
**审计字段说"没过滤"，越界数字说"过滤了"**。

### 6.2 根因：过滤被接了两层

| 位置 | 是否执行 |
|---|---|
| 评测脚本的 `retrieve_fn` 外层（脚本自己包的） | ✅ 执行 |
| `retrieval` 节点内部（**生产接线**） | ❌ **没执行** |

**为什么节点内没执行**：`run_turn` 内部调用 `get_config()`（带 `@lru_cache`），
**不接收外部传入的 cfg**。测试里 `cfg = dict(get_config()); cfg[...]=True` 改的是副本。

### 6.3 危害（比"没过滤"更严重）

- 数字看起来对，但**测的不是生产路径** —— 节点内接错了评测照样绿；
- 审计字段全空，**误杀无法复查**；
- on/off 两臂实际是"脚本外层开关" vs "节点内开关"，**不是同一件事的对照**。

### 6.4 修正

```python
os.environ["TOPIC_FILTER_ENABLED"] = "true" if filter_on else "false"
app.config.get_config.cache_clear()
cfg = get_config()
assert bool(cfg["topic_filter_enabled"]) is filter_on   # 断言开关真生效
```

`retrieve_fn` 改为**只检索，不过滤** —— 过滤唯一入口是节点内。

**教训**（已写入 ADR-0002 §6.4）：

> **凡"评测脚本包一层、生产代码里也有一层"的地方，必须先断言"生产层真的执行了"。**
> 判据不是"结果变好了"，而是"**审计字段有值**"。

**本报告 §2/§3 的所有数据均来自修正后的版本。**

## 8. 已知限制（必须随报告一起引用）

> **过滤参数以 5 篇语料 / 35 题标定，新语料泛化未验证，上线新文档集前须重扫阈值。**

- `min_consistency = 1.0` 是在本语料上扫出来的最优值（阈值扫描曲线见 ADR-0002 §8.6）
- 1.0 与 1.5 之间只隔一道边界（`q029` 的 gold chunk 分数**恰好 = 1.00**）
- 这个边界的宽窄**完全取决于语料** —— 换文档集，1.0 可能过严也可能过松
- **重扫方法**：`scripts/spike_v11/s5b_threshold_scan.py`
- **机制守卫**：`test_boundary_sentinels.py::TestOverfitGuard`（默认阈值/开关/文档三者锁定）

**为什么这条非写不可**：不写，将来换语料后 Recall 崩了，**没人知道是阈值问题** ——
只会去查检索、查模型、查 chunk，查三天也查不到一个从未被记录过的假设。

## 10. 结论与建议

### 10.1 结论

1. **四项赌注全部 PASS**，且数据来自**修正后的生产路径**（审计字段有值）。
2. **filter 是有效主药**：越界 −91.6%，Recall 零损失，MRR 反升，延迟无劣化证据。
3. **filter 不是万能的**：残留 0.7/轮，形态是"正确片段内部不支撑"（critic 的靶子）。
4. **参数过拟合是已知限制**，已写入 ADR-0002 §6.2 + 测试守卫。

### 10.2 建议

| # | 建议 | 理由 |
|---|---|---|
| 1 | **本迭代打 tag v1.1** | FB1–FB4 全 PASS，门禁全绿 |
| 2 | **critic 立项 V1.2**，靶子 = §4 残留 | 已在 ADR-0002 §4 逐字存档 |
| 3 | **换语料时必跑阈值重扫** | §8 已知限制 |
| 4 | `TOPIC_FILTER_ENABLED` **默认 on**（保证部署行为与报告一致）；换语料前先重扫阈值，或临时置 false | 过拟合风险（ADR-0002 §6.2） |

### 10.3 明确的"不做"

- **不宣称"引用越界已根治"**
- **不宣称"filter 提升性能"**（CI 上界跨 0，只能排除显著变慢）
- **不宣称"检索质量全面提升"**（Recall 持平，只有 MRR 提升）

### 11.2 端到端真机验证（HTTP → Go → Python → DB）

**请求**：`POST /api/v1/sessions/{id}/messages`
`{"question": "Kubernetes 的 livenessProbe 和 readinessProbe 应该怎么配置？"}`

**结果**：`answer_type=answered`、`citations=1`、**`overreach=0`**

**trace 落库（DB 直查，这是关键证据）**：

```

```

→ **5 个检索片段剔除 4 个、保留 1 个**，锚点数 2。
**过滤在生产路径真实执行**（不是脚本外层的效果，见 §6 的教训）。

### 11.3 一处必须说清的边界：`topic_filter` 未出现在 HTTP 响应里

| 层 | 是否含剔除明细 |
|---|---|
| Python `run_turn` 的 result | ✅ 有 |
| Go 落库的 `run_steps.output_summary` | ✅ 有（`filtered_out` / `anchors`） |
| **HTTP 响应 JSON** | ❌ **无** |

**原因**：Go 侧 `TurnResult` 结构体未声明 `topic_filter` 字段
（与 `retrieved_chunk_ids` 同等情况，属"内部字段不对外"的既有设计）。

**影响评估**：

- **ADR-0002 §7 的要求是"剔除写 trace"** —— 已满足（DB 可查）；
- 前端不需要展示剔除明细（它属于运维审计信息，不是用户体验的一部分）；
- **不构成缺陷**，但**必须记录**，避免将来有人误以为"响应里没看到 = 没生效"。

**若将来需要在 UI 展示**（例如调试面板），需在 Go `TurnResult` 加字段 + 前端渲染，
属独立需求，不在本迭代范围。
