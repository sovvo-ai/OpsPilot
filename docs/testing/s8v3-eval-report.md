## 3. 校准日志（本轮改动与实证）

### 3.1 本轮为修缺陷做的改动（都会影响本轮数字）

| 改动 | 目的 | 影响 |
|---|---|---|
| `retrieve(probe=True)` + `State.probe_chunk` | 让拒答能列出"最高分片段"（PRD §7.4 硬要求） | 拒答文案变完整；不影响 Recall |
| `REF_MARK_RE` 接受 `<n>` + `normalize_ref_marks` | 模型偶尔输出 `<1>`，早期**静默丢失**该引用 | 引用 ID 有效率仍 1.000 |
| prompt 新增"编号必须与主题匹配" | 防跨文档引用错配 | 见 3.2 |
| `citation_overreach` 检测（S9 前一提交引入） | 观测"引用存在但不支撑" | 见 3.2 |

### 3.2 ⚠️ `m001` 复现结论（与 v2 人工复核的关联）

**v2 人工复核把 `m001` 判为「不支撑」**（引用越界），据此立项 `S9-PRE-1` 收紧引用纪律。
本轮**重跑 5 次采样**，`citation_overreach` 检测**每次都有命中**（1–4 处），
涉及 token：`livenessProbe` / `readinessProbe` / `startupProbe` / `periodSeconds` 等。

**逐层定位（实测）**：

1. **不是检测器误报**：核对被引片段的**完整原文**后确认，某次答案把
   `[2]` 给了《Linux 网络故障排查》片段（该片段**完全不含探针内容**），
   却用它支撑"livenessProbe 失败会导致容器重启" —— **真实越界**。
2. **检索噪声是主因**：m001 的检索集（5 条）里稳定混入
   `linux-network-troubleshooting` / `nginx-502-upstream` 等**与探针无关**的文档，
   模型有时挑中了它们。
3. **改写本身是生效的**（实测 `rewritten_query="如何配置 Pod 的探针？"`，
   `rewritten=True`），说明 FR-17 链路正常；问题在**改写后的检索仍带回无关文档**，
   而模型没能稳定守住"编号必须与主题匹配"。
4. **prompt 收紧有效但不充分**：答案里已出现正确表述
   （`（模型通用知识，无 KB 出处）：… 故不标注编号`），但**跨文档错配未被完全消除**。

**结论（诚实标注）**：
- **`m001` 的支持率未回到 1.000**；v3 的该项留给人工复核（`NOT RUN`），
  **不预设它会上升**。
- 检测器（`citation_overreach`）已把问题**变成可观测、可回归的**，这本身是净改进
  （v2 时该问题机器完全抓不到）。
- **后续待办（不在本轮）**：① 检索层加"文档主题相关性"过滤（按 doc_title/关键词
  与问题的重合度裁剪无关文档）；② 或对 rewrite 后的查询做**二次检索收敛**。
  这两项都属行为改动，需单独评估对 Recall 的影响，**不塞进收尾提交**。
