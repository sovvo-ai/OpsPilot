## 1. 背景与要解决的问题

### 1.1 背景

运维/开发排查故障时的真实动作是：翻文档（知识散落在 Markdown、Wiki、内部笔记里）→ 看日志（报错文本粘来粘去）→ 凭经验猜 → 验证。三个断点：

1. **知识检索低效**：关键词搜索命中率差，找到的文档片段对不上当前症状。
2. **结论不可追溯**：通用大模型能给出看似合理的排障步骤，但无法说明依据来自哪份文档、哪一段。运维不敢照着执行。
3. **诊断过程不可复现**：人和人的排障过程无法沉淀，出问题只能重来一遍。

### 1.2 本项目要解决的问题

| 问题 | OpsPilot 的应对 |
|---|---|
| 知识检索低效 | 文档切片 + 向量检索（pgvector），按语义而非关键词召回 |
| 结论不可追溯 | 每个结论必须绑定 chunk 级引用，引用可回溯到原文片段；无证据则拒答 |
| 过程不可复现 | LangGraph 固定节点编排 + 全链路执行轨迹落库，可回看每一步 |
| 模型可能乱来 | 受控工具白名单（纯函数、只读、不执行命令）+ 证据校验节点 |

### 1.3 项目定位（必须说清楚）

这是一个**面向 AI 应用开发岗位的求职项目**，不是商用产品。因此：

- 评价标准不只是"功能跑通"，还包括"技术决策能否讲清楚""演示能否 3 分钟打动人"。
- 不做多租户、不做计费、不做高可用集群 —— 这些不在面试考察范围内，做了反而稀释重点。
- 允许在文档中标注"当前实现为演示规模"，但**不允许在功能上假装支持**。

### 2.2 使用场景

| # | 场景 | 输入 | 期望输出 |
|---|---|---|---|
| S1 | 概念/操作查询 | "Pod 一直 CrashLoopBackOff 怎么排查？" | 分步排查建议 + 引用文档片段 |
| S2 | 报错定位 | 粘贴一段错误日志 + "这是什么问题" | 错误类型识别 + 相关文档 + 可能的根因候选（标注不确定） |

### 2.3 非目标用户

- 需要企业级权限体系、审计合规、SLA 承诺的正式生产环境使用者。
- 期望接入真实主机、自动执行修复动作的用户（V1 明确只读且不触达主机）。

## 3. 产品目标与成功指标

### 3.1 产品目标（V1）

| # | 目标 | 衡量方式 |
|---|---|---|
| G1 | 上传的技术文档可被召回到正确片段 | Recall@5 ≥ 0.75 |
| G2 | 回答有据可查，无据不编 | 引用 ID 有效率 100%（A3）+ 引用内容支持率 ≥ 0.90（A3b）+ 拒答正确率 ≥ 0.85 |
| G3 | 多步诊断可用且过程可见 | 任务成功率 ≥ 0.70；每次会话有完整轨迹 |
| G4 | 一键可跑 | 干净环境 `docker compose up -d` 到冒烟通过 ≤ 5 分钟 |

- 不做 DAU / 留存 / 转化 —— 演示项目没有真实用户。
- 不用"回答得像不像人"作为指标 —— 无法量化，且与"有据可查"目标冲突。

## 5. 用户角色与核心流程

### 5.1 角色与资源归属

**准确表述**：V1 是「**无注册页面的开发演示环境**」，不是"单用户产品"。系统支持两个白名单身份，仅用于开发、测试与隔离验证；没有注册页、登录页、密码、找回流程。v1.0 写的"单用户"是含糊说法，掩盖了必须做隔离这件事。

| 身份 | 权限范围 | 获取方式 |
|---|---|---|
| `demo-user` | 上传/提问/查看/删除**自己的**资源 | `POST /auth/dev-token`（仅 dev 环境） |
| `test-user-2` | 同上，仅自己的资源；**仅用于跨用户隔离测试** | 同上，`user=test-user-2` |
| 匿名 | 无权访问任何业务接口 | — |

> V1 不区分管理员与普通用户，也没有"文档对所有登录者开放"这回事：**每个身份只能操作自己的文档**。

**资源归属表**：

| 资源 | 归属字段 | 归属来源 | 必须校验归属的操作 |
|---|---|---|---|
| `documents` | `owner_id` | JWT `sub` | 上传（写入）、查看、删除、reingest、去重查询 |
| `document_contents` | 随 `documents` | 同上 | 不单独暴露接口，只经文档访问 |
| `ingest_jobs` | 随 `documents` | 同上 | 查状态、触发重试 |
| `doc_chunks` | 随 `documents` | 同上 | 检索时**必须**按 owner 过滤；引用回显按 owner 校验 |
| `sessions` | `owner_id` | JWT `sub` | 创建、列表、重命名、删除 |
| `messages` | 随 `sessions` | 同上 | 读取、追加 |
| `agent_runs` | `owner_id` | JWT `sub` | 查看轨迹 |
| `tool_calls` | 随 `agent_runs` | 同上 | 随轨迹返回 |

**四条硬规则**：

1. 所有按 ID 访问的接口必须校验 owner；不匹配一律返回 **404**（不是 403 —— 403 会泄露"该资源存在"）。
2. 检索类操作（含 `search_knowledge_base` 工具）必须限定在当前 owner 的文档集合内，不得跨用户召回。
3. **去重唯一索引必须是 `(owner_id, source_hash)`，不能是全局 `source_hash`**。否则 `test-user-2` 上传与 `demo-user` 相同内容的文件时会命中对方文档，`deduplicated=true` 直接返回对方的 `doc_id` —— 这是跨用户信息泄露，不是小问题。
4. 不因"演示项目"跳过隔离。A13 是 P0 验收项，不属于"可选加固"。

### 5.2 核心流程 A：知识入库（异步）

```
运维上传 .md/.txt
   │
   ├─ 前置校验（Go 侧，拿到字节即可判断，不落库）
   │    · 类型 .md/.txt   · 大小 ≤5MB   · 编码 UTF-8/GBK   · 非空
   │    任一失败 → 4xx，documents 无新行
   │
   ├─ 规范化：NFC + 换行统一 + 去 BOM
   ├─ 去重：sha256(规范化全文) + **同一 owner** 命中 → 返回既有 doc_id（跨用户不比对）
   │         （若既有文档为 failed，附带 retry_hint，不静默跳过）
   ├─ 落库：documents(元数据) + document_contents(正文) + ingest_jobs(pending)，同事务
   │
   ├─ 立即返回 202 {doc_id, ingest_status:"pending", poll_url}
   │
   └─ 后台派发（goroutine；不引入队列）
        ├─ ① 抢占：pending → processing（原子条件更新，attempt+1，生成 run_token）
        ├─ ② 调 Python /internal/v1/ingest（读超时 120s）
        │      · 切片 400~600 字符 / 重叠 80
        │      · Embedding 每批 ≤10 条、1024 维
        │      · 写 doc_chunks 时 visible=false、带 run_token
        │      · 不写 ingest_jobs
        ├─ ③ Python 返回 {run_token, status, chunk_count}
        ├─ ④ Go 发布（单事务）：run_token CAS → completed
        │      + 本世代 visible=true
        │      + 删除旧世代切片
        └─ ⑤ 失败：CAS → failed(error_code)；清本次可见=false 切片
```

为什么要异步：同步实现会让上传请求挂 30s，`pending/processing` 用户永远看不到，与前端 2s 轮询（UI-01）设计脱节。异步后状态机才真正有意义。

用户可见：上传后立刻看到文档与 `pending` 状态 → 轮询变 `processing` → `completed` 可检索；`failed` 时显示原因 + 「重试」按钮（调 `POST /documents/{id}/reingest`）。

**Go → Python 调用约束**：连接超时 3s、读超时 120s。**超时后 Go 不得直接改写 `processing` 任务的终态**（那会与 Python 竞争），只记录"调用方超时"，最终状态以 §5.7 的收敛规则为准。不引入消息队列 —— V1 用进程内 goroutine；进程重启会丢失在途任务，由 §5.6 的 watchdog 在启动后首轮扫描收敛。

### 5.3 核心流程 B：提问与回答

```
提问
  │
  ├─ Router：判定 kb_qa / troubleshooting / smalltalk / out_of_scope
  │    （规则命中直接判定，不确定才问模型）
  │
  ├─ 指代追问？（非首轮 + 有指代词）→ Query Rewrite 改写一次
  │
  ├─ 检索：向量 top-5 + 相似度阈值 + 仅 completed 文档
  │    └─ 全部低于阈值 → 拒答（不进入生成）
  │
  ├─ 若为 troubleshooting：调工具（≤3 次）→ 生成诊断
  │
  ├─ 证据校验：引用 ID 必须存在且属于本次检索集（代码强制）
  │              结论是否有片段支撑（规则优先，存疑才问模型）
  │
  └─ 生成最终回答 + 引用列表 + 轨迹落库
```

用户可见：回答、引用（可点开原文片段）、"是否降级"的提示、轨迹入口。

### 5.4 核心流程 C：复盘

打开历史会话 → 看到消息列表 → 点击某条回答 → 侧栏展示：走了哪些节点、每节点耗时、调用了几次模型（含模型名与 token）、调用了什么工具（入参摘要与耗时）、是否降级及原因。

### 5.5 数据归属与写入职责（Q1 决策后）

> v1.2 让 Python 写任务终态，等于"双方都能写终态"，必须加锁或两阶段提交才能防覆盖。v1.3 按 Q1 决策改为：**任务状态全部归 Go，Python 只产数据不决状态。**

| 表 | INSERT | UPDATE | 只读 |
|---|---|---|---|
| `documents` | **Go** | **Go**（元数据、`deleted_at`） | Python |
| `document_contents` | **Go**（与 `documents` 同事务） | Go | Python（摄取时读原文） |
| `ingest_jobs` | **Go**（`status=pending`） | **Go 独占**，含全部状态迁移与终态收敛 | Python 只读 `current_run_token` / `attempt` |
| `doc_chunks` | **Python**（写内容，`visible=false` + `run_token`） | **Go** 只改 `visible`（发布）与按 token 清理；Python 不改可见性 | 双方各读所需字段 |
| `sessions` / `messages` | **Go** | Go | Python（只读上下文） |
| `agent_runs` / `tool_calls` | **Go** | Go | — |

`doc_chunks` 是**受约束的双写例外**：Python 只能 `INSERT`（不可见）与 `DELETE WHERE doc_id=$1`；Go 只能 `UPDATE visible=true WHERE run_token=$t`。两侧都不碰对方负责的字段。

> 详细协议、SQL 与边界见 `docs/architecture/ingest-consistency.md`。

### 5.6 任务状态机

**五个状态**：`pending | processing | completed | failed | deleting`

```
                     watchdog: pending 超 120s
                     ┌──────────────────────────► failed(DISPATCH_FAILED)
                     │
上传 → pending ──claim──► processing ──发布成功──► completed
                              │
                              ├── Python 返回失败 ──► failed(PARSE_ERROR / EMBEDDING_FAILED / …)
                              └── watchdog: 超 150s ─► failed(TIMEOUT)

failed ──reingest──► pending        （attempt 在下次 claim 时 +1）
任意状态 ──delete──► deleting ──清理完成──► 行删除
```

| 状态 | 可检索 | 可 reingest | 可删除 |
|---|---|---|---|
| `pending` | 否 | 否（409 `DOC_BUSY`） | 是 |
| `processing` | 否 | 否（409 `DOC_BUSY`） | 是 |
| `completed` | **是** | 否（409 `DOC_NOT_RETRYABLE`） | 是 |
| `failed` | 否 | **是** | 是 |
| `deleting` | 否 | 否（409 `DOC_DELETING`） | 幂等 202 |

**抢占规则（Q3 / Q5）**：

- 抢占是**一条原子条件更新**，且**只接受 `pending`**：`WHERE status='pending'` → 置 `processing`、`attempt+1`、写入新 `run_token`、记 `started_at`、刷 `updated_at`。影响行数 0 即抢占失败，直接放弃，不向用户报错。
- **`failed` 不能直接被抢占**：必须先经 `reingest` 回到 `pending`。允许 `failed→processing` 等于任何游离执行者都能复活失败任务，与"V1 不自动重试"矛盾。
- `attempt` 表示**已执行次数**：建行默认 **0**，每次成功抢占 +1，首次执行后为 1；`reingest` 请求本身不递增。
- `run_token`：32 位小写 hex，`crypto/rand` 生成；每次抢占重新生成；只通过请求体传给 Python，Python 原样回带；**Go 发布会校验它**。
- V1 不引入显式锁。批量抢占若将来确有需要，再评估 `FOR UPDATE SKIP LOCKED`。

**恢复规则（Q1 / C）**：`pending` 与 `processing` **都必须被扫描**。只扫 `processing` 会把"未被派发"的任务永久卡死。

| 场景 | 判定 | 处理 | 可否重试 |
|---|---|---|---|
| `pending` 超 120s | 任务从未被抢占 | Go watchdog → `failed(DISPATCH_FAILED)` | 是 |
| `processing` 超 150s | 执行中断或挂死 | Go watchdog → `failed(TIMEOUT)`，并清该 token 的不可见切片 | 是 |
| Go 进程重启 | 在途派发全丢 | 启动后**立即**跑一轮 watchdog，不等 60s | 是 |
| Python 进程重启 | 在途 `processing` 成孤儿 | 由 Go watchdog 收敛；**不自动重跑** | 是 |
| 两个 watchdog 同时收敛 | 理论可能 | 条件更新只有一方生效 | — |

**V1 不自动重试**：`failed` 后必须用户显式 `reingest`。`attempt` 只作执行世代标识，不设上限。理由：无队列的自动重试会反复烧 Embedding 费用，且用户看不到重试节奏。

### 5.7 两阶段发布与超时收敛（Q2 / A）

**核心事实：Go 的读超时 ≠ Python 停止执行。** 所以"调用成功"不能直接等于"数据生效"。

**协议**（细节见 `ingest-consistency.md` §4）：

1. Go 抢占后调 `POST /internal/v1/ingest`，带 `job_id / doc_id / run_token / attempt`。
2. Python 解析、切片、Embedding，写 `doc_chunks` 时置 **`visible=false`** 并带 `run_token`；**不写 `ingest_jobs`**；返回 `{run_token, status:"ok", chunk_count}`。
3. Go 在**自己的事务**里发布，这是唯一生效闸门：

```sql
UPDATE ingest_jobs
   SET status='completed', published_run_token=$token, finished_at=now(), chunk_count=$n
 WHERE id=$job AND status='processing' AND current_run_token=$token;
-- 影响 0 行 → 回滚，记审计 stale_result_dropped，丢弃

UPDATE doc_chunks SET visible=TRUE WHERE doc_id=$doc AND run_token=$token;
DELETE FROM doc_chunks WHERE doc_id=$doc AND run_token IS DISTINCT FROM $token;
```

**为什么旧执行无法发布过期向量**：不可见切片永不参与检索；发布必须通过 `run_token` 的 CAS；旧世代在发布时被物理删除。三重保证缺一不可。

**承诺（可验收）**：

| # | 承诺 |
|---|---|
| 1 | 以数据库终态为准。Go 超时后不得断言"失败"，也不得改 `processing` 的终态 |
| 2 | 谁先提交终态谁算数，后者影响 0 行并被丢弃（审计 `stale_result_dropped`） |
| 3 | 不存在"状态 completed 但检索不到切片"或"未完成却能检索到切片"（`visible` + 状态双过滤保证） |
| 4 | 中间态如实返回 `processing`，**不猜测成 `failed`** |
| 5 | 不自动重试，一律等 watchdog 定论或用户显式重试 |
| 6 | **零切片闸门**：Python 返回 `chunk_count=0` 时 Go 一律置 `failed(EMPTY_CONTENT)`，绝不发布"completed + 0 可见切片"。否则直接击穿 A14② |

### 5.8 删除流程（Q4）

**引入 `deleting` 状态。** 替代方案是"先删向量再删记录"或反之，两者都会留窗口：记录没了向量还在（召回幽灵片段），或向量成孤儿无人清理。`deleting` 把窗口显式化：检索立即不可见，用户能看到"删除中"，watchdog 持续重试直到清干净。

```
DELETE /documents/{id}
  ├─ 校验 owner → 不符返回 404
  ├─ CAS: 任意状态 → deleting；deleted_at=now()；current_run_token=NULL（使在途执行失效）
  ├─ 202 {status:"deleting"}
  └─ 后台清理：调 Python 按 doc_id 全删切片 → Go 单事务删三表 → 完成
       失败则保持 deleting，watchdog 每 60s 重试
```

**硬性约束**：

1. 清理未完成前**绝不删除 `documents` 行** —— 否则遗留无主向量，这正是本设计要防的核心错误。
2. Python 清向量必须**按 `doc_id` 全删**（含 `visible=false`），不按 token 过滤。
3. `deleting` 状态拒绝检索、拒绝 `reingest`、拒绝读正文。
4. `deleting` 期间重复删除 → 202 幂等，不新建清理任务。

**与在途执行的关系**：删除把 `current_run_token` 置 NULL，在途 Python 返回时 CAS 必然失败 → 结果丢弃，切片按 `doc_id` 清掉。

## 7. 多 Agent 的用户可见行为

> 用户不需要知道"什么是 Agent"，但必须能预期系统会怎么反应。以下是**对外承诺的行为**，不是内部实现描述。

### 7.1 路由优先级（判定顺序，命中即短路）

> v1.1 只说了"何时走哪条"，没说"谁先判"。结果是实现时容易变成"一切先检索再说"，寒暄也去查知识库。以下顺序是硬约定。

| 顺序 | 判定 | 结果 | 是否检索 | 是否生成 | 说明 |
|---|---|---|---|---|---|
| 1 | 输入非法（空 / >500 字） | 422 `INVALID_QUESTION` | 否 | 否 | 前置校验，不进图 |
| 2 | `smalltalk` 强命中（你好 / 谢谢 / 在吗 / 你是谁 / 能做什么） | → Smalltalk 节点 | **否** | 否（固定文案） | 寒暄查知识库是荒谬行为，零成本处理 |
| 3 | `out_of_scope`（写代码 / 翻译 / 通用闲聊 / 与本系统无关的任务） | → 越界拒绝 | **否** | 否（固定文案） | 明确说明"只处理技术文档问答与故障排查" |
| 4 | `troubleshooting` 特征（堆栈 / `error` / `failed` / 错误码 / 异常类名 / 端口+"起不来"） | → 检索 + 工具 + 诊断 | 是 | 是 | 见 §7.3 |
| 5 | 其余 | → `kb_qa` | 是 | 是 | 见 §7.2 |

规则：
- **顺序即优先级，命中即停止判断**，不允许"先检索看看再说"。
- 只有第 4、5 档进入检索；第 2、3 档**零检索、零生成**（Router 自身可能在规则不确定时调 1 次模型，但模型只能输出这 4 类之一）。
- 规则不确定时**默认 `kb_qa`**（宁可多检索一次），但 `smalltalk` / `out_of_scope` 只在词典或模式**强命中**时生效，不做模糊判断。
- 同一输入同时命中 3 与 4 时，**3 优先**（越界优先于诊断）：越界任务不该消耗工具调用预算。

### 7.2 何时走 RAG（知识问答）

触发条件（满足任一）：
- 问题在问概念、操作步骤、配置方法、原理。
- 携带"怎么/如何/是什么/为什么/区别"类疑问词。
- 未检测到日志特征（堆栈、时间戳、错误码、`Exception` 等）。

用户看到：一段结构化回答 + 引用列表 + 展开原文。

### 7.3 何时走故障排查

触发条件（需同时满足）：
- 输入包含日志/错误特征（堆栈、`error`、`failed`、错误码、异常类名、端口号 + "起不来"等）。
- 或用户显式要求诊断（"帮我看看这段日志""为什么 8080 起不来"）。

用户看到：错误类型识别 → 相关文档依据 → **按可能性排序的排查步骤** → 用到的工具与结论依据。

### 7.4 何时拒答

| 情况 | 用户看到 |
|---|---|
| 检索全部低于相似度阈值 | "未在知识库中找到与该问题相关的资料" + **列出它检索到的最高分片段及分数**（让用户判断是不是文档缺失） |
| 有检索结果但证据不支持结论 | 只输出被证据支持的部分，未支撑部分明确标为"以下为推测，未找到文档依据" |
| 追问脱离上下文（无法确定指代对象） | "你指的是哪个对象？" + 给出 2~3 个候选，不猜 |

**硬规则**：任何情况下不得输出"根因是 X"这类确定性结论，除非有引用片段或日志证据直接支持。违反即为 P0 缺陷。

### 7.5 降级的用户可见表现

| 降级原因 | 用户看到 |
|---|---|
| 模型超时 | 正常回答 + 角标"本次回答未完成深度校验" |
| 预算耗尽 | 正常回答 + 角标"本次回答省略了部分校验" |
| 工具失败 | 回答中注明"日志分析工具调用失败，以下结论仅基于文档" |
| 改写失败 | 无提示（内部降级，不影响用户理解） |

**不允许**：降级时静默返回一个看起来完全正常的答案。用户有权知道答案的可信度。

### 8.5 SSE 契约设计事项（行为在此定，字段留给 API 契约阶段）

| # | 事项 | PRD 必须定下的行为 |
|---|---|---|
| S1 | 事件类型 | 至少区分 `meta`（run_id / session_id）、`delta`（增量文本）、`citation`（引用，**流结束后一次性发**，不在流中插半截引用）、`done`（正常结束，含 usage 摘要）、`error`（异常结束，含 code） |

| S6 | 客户端不支持流 | 回退为非流式一次性返回（同一份回答内容） |

验收：U9（§11.5）+ 一条"断流后 trace 标记 `interrupted` 且预算已停止消耗"的后端测试。

## 9. 异常与错误处理

### 9.1 统一错误结构

```json
{"error":{"code":"DOC_TOO_LARGE","message":"文件超过 5MB 限制","request_id":"..."}}
```

### 9.2 错误码表（用户可见部分）

| 场景 | HTTP | code | 用户可见文案 | 系统行为 |
|---|---|---|---|---|
| 文件格式不支持 | 415 | `UNSUPPORTED_FORMAT` | 仅支持 .md 与 .txt 文件 | **前置拒绝，不落库** |
| 文件超过 5MB | 413 | `DOC_TOO_LARGE` | 文件超过 5MB 限制，请拆分后上传 | **前置拒绝，不落库** |
| 编码无法识别 | 422 | `ENCODING_ERROR` | 无法识别文件编码，请转为 UTF-8 | **前置拒绝，不落库** |
| 文件内容为空 | 422 | `EMPTY_CONTENT` | 文件内容为空 | **前置拒绝，不落库** |
| 文档处理中 | 409 | `DOC_BUSY` | 文档正在处理，请稍后再试 | 不执行删除 / 不受理重复重试 |
| 文档已完成，无需重试 | 409 | `DOC_NOT_RETRYABLE` | 该文档已处理完成 | 拒绝 reingest |
| 文档正在删除 | 409 | `DOC_DELETING` | 文档删除中，无法操作 | 拒绝读正文 / reingest；重复删除仍返回 202 |
| 知识库为空 | **200** | `KB_EMPTY`（业务态） | 知识库还没有可用文档，请先上传 | 不调模型，生成引导文案 |
| 检索无结果 | 200 | `NO_EVIDENCE`（业务态） | 未找到相关依据 + 最高分片段 | 走拒答分支 |
| 提问为空/超长 | 422 | `INVALID_QUESTION` | 问题不能为空且不超过 500 字 | 不落库 |
| 模型超时 | 200 + 降级标记 | `MODEL_TIMEOUT`（trace 内） | 正常回答 + "未完成深度校验" | 降级继续 |
| 模型不可用 | 503 | `MODEL_UNAVAILABLE` | 智能服务暂时不可用，请稍后重试 | 不重试到底 |
| 工具执行失败 | 200 + 降级标记 | `TOOL_FAILED`（trace 内） | 回答注明"工具调用失败" | 降级继续 |
| 工具名不在白名单 | 400 | `TOOL_NOT_ALLOWED` | 不支持该操作 | 拒绝并记录 |
| 数据库不可用 | 503 | `DB_UNAVAILABLE` | 服务暂时不可用 | `/health/ready` 同时 503 |
| 未认证 | 401 | `UNAUTHORIZED` | 请先获取访问令牌 | — |
| 无权限访问资源 | 404 | `NOT_FOUND` | 资源不存在 | 不泄露存在性 |
| 内部调用鉴权失败 | 401 | `INTERNAL_AUTH_FAILED` | （仅内部） | 拒绝，记 `token_fp` |

> **`KB_EMPTY` 从 409 改为 200 的理由**：它与"检索无结果"(`NO_EVIDENCE`) 同属"服务正常、但无内容可答"的业务态，用 4xx 会被前端错误处理逻辑当成请求错误弹红框。统一为 `200 + 业务态 code + 引导文案`，前端只需判断 `answer_type`。
>
> **本表是错误码的唯一权威版本。** §9.3 阶段表只描述"何时触发"，不重复定义 code；接口层新增错误码必须先加到本表。

### 9.3 错误语义分界线：以"落库时点"一刀切

**唯一规则**：Go 在落库前能判定的一律 4xx 且不落库；落库之后才能发现的一律用"文档状态"表达，HTTP 仍是 2xx。

| 阶段 | 判定方 | 错误码 | HTTP | 是否落库 | 用户怎么知道 |
|---|---|---|---|---|---|
| 前置校验 | Go（拿到字节即可判断） | `UNSUPPORTED_FORMAT` / `DOC_TOO_LARGE` / `ENCODING_ERROR` / `EMPTY_CONTENT` | 415 / 413 / 422 / 422 | **否** | 上传响应直接报错 |
| 已受理 | Go | — | **202** | 是 | 响应含 `doc_id` + `ingest_status=pending` + `poll_url` |
| 摄取期失败 | Python | `PARSE_ERROR` / `EMBEDDING_FAILED` / `RATE_LIMITED` / `TIMEOUT` | 查询接口 200；重试接口 202 | 是 | 轮询 `GET /documents/{id}` 看到 `ingest_status=failed` + `error_code` + `error_msg` |
| 基础设施 | 任一侧 | `DB_ERROR` | 503 | 可能部分 | `/health/ready` 同步 503 |

**任务层错误码 → 用户可见位置**（阶段 0 §7.1 的枚举，不允许另造新码）：

| `ingest_jobs.error_code` | 出现位置 | 可重试 | 说明 |
|---|---|---|---|
| `PARSE_ERROR` | `GET /documents/{id}` 的 `error_code` | 否（需修正文件后作为新文档上传） | 解析失败发生在切片阶段，此时文件已落库 |
| `EMBEDDING_FAILED` | 同上 | 是（`reingest`） | 服务端问题 |
| `RATE_LIMITED` | 同上 | 是（`reingest`，建议隔 60s） | 退避重试已耗尽 |
| `TIMEOUT` | 同上 | 是（`reingest`） | 摄取超时，由 watchdog 收敛（§5.7），不是 Go 直接写 |
| `DISPATCH_FAILED` | `GET /documents/{id}` 的 `error_code` | 是（`reingest`） | `pending` 超 120s 未被抢占（Go watchdog 写入） |
| `EMPTY_CONTENT` | 同上 | 否 | 两个来源：①解码后为空（前置已拦，正常不出现）②**Python 返回 `chunk_count=0` 被 Go 拒绝发布**（§5.7 零切片闸门） |
| `DB_ERROR` | 响应 503 `DB_UNAVAILABLE` + job failed | 是 | 基础设施故障 |

**v1.0 的两处自相矛盾（已修）**：
1. `ENCODING_ERROR` / `EMPTY_CONTENT` 在 §9.2 写"状态 failed"——但状态 failed 意味着已落库，与"4xx 不落库"冲突。现统一为**前置拒绝、不落库**。
2. `PARSE_ERROR` 被映射成 422——但解析失败发生在摄取期，文件早已落库，违反本节规则。现统一为**200 + 状态 failed**。

> 附带效果：因为上传是异步的（§5.2），上传响应**永远**是 202 或前置 4xx，摄取失败不可能出现在上传响应里。这是设计上的必然，不是遗漏；前端必须通过轮询拿状态。

### 9.4 异常场景逐条验收

| 场景 | 期望 |
|---|---|
| 上传二进制文件改名成 .md | 返回 422 `ENCODING_ERROR`，**`documents` 表无新行** |
| 上传成功但摄取失败（模拟 Embedding 报错） | 上传返回 202；轮询 `GET /documents/{id}` 见 `ingest_status=failed` + `EMBEDDING_FAILED`；`documents` 有行、`doc_chunks` 为空（事务已回滚） |
| **failed 文档手动重试** | `POST /documents/{id}/reingest` → 202；修复依赖后重试 → `completed`；切片总数与单次成功摄取一致（无重复）；再次重试已 completed 的文档 → 409 `DOC_NOT_RETRYABLE` |
| 重复上传一篇已 failed 的文档 | 返回 `deduplicated=true` + `ingest_status=failed` + `retry_hint`，**不静默跳过、不重新摄取** |
| 知识库为空时提问 | HTTP **200** + `KB_EMPTY` 业务态，**不调用任何模型**（mock 断言 0 次） |
| 检索无结果 | 走拒答分支，输出最高分片段及分数，`llm_calls ≤ 2` |
| 模型超时 | 单节点降级，整体仍返回答案，`degraded=true` |
| 工具超时 | 5s 后放弃，回答注明，不阻塞整轮 |
| Python 服务挂掉 | Go 返回 503 `MODEL_UNAVAILABLE`，Go 自身 `/health/live` 仍 200；在途 job 由 watchdog 在下一轮扫描收敛为 `failed` |
| 数据库挂掉 | `/health/ready` 503，业务接口 503 `DB_UNAVAILABLE` |
| 删除文档后看历史 | 200，引用 `status=deleted` |
| 并发上传同一文件 | 一个返回 202 落新行、一个返回 `deduplicated=true`，不重复计费 |
| 删除进行中访问该文档 | `GET` 返回 200 + `ingest_status=deleting`；读正文/重试返回 409 `DOC_DELETING` |
| 删除后 Python 迟到返回结果 | CAS 失败 → 结果丢弃，记 `stale_result_dropped`；向量由按 doc_id 清理删除，库中无残留 |
| 文档停在 `processing` 超过 150s | watchdog 收敛为 `failed(TIMEOUT)`，该文档不可检索，可 reingest |
| 文档停在 `pending` 超过 120s | watchdog 收敛为 `failed(DISPATCH_FAILED)`，不复用旧 goroutine |
| 两个用户上传完全相同内容 | 各自建档，`deduplicated=false`，互不可见对方 `doc_id` |

## 12. V1 与 V2 的功能边界

| 能力 | V1 | V2 |
|---|---|---|
| 文档格式 | Markdown / TXT | + PDF / DOCX / HTML |
| 检索 | 纯向量 + 阈值 | + BM25 混合 + rerank |

| 权限 | 无 RBAC | 角色权限、文档级授权 |
