## 3. 依据（三臂对照实测，不引立场只引数字）

| 臂 | 配置 | 有越界 run | 越界总数 | Recall@5 | MRR@5 |

**"覆盖不到病灶"是淘汰 critic 的唯一理由，成本只是加分项。**

## 4. V1.2 立项证据（条件 ①：残留 1/15 逐字存档）

**这是 critic 未来的靶子，必须逐字保留。**

三臂对照 C 臂中，`q001` 第 5 轮仍有 **1 处越界**。原文记录：

> **C 臂残留 1 处必须记录**：`q001` 第 5 轮。说明过滤解决"污染进入引用池"（主因），
> 但**正确片段内部本身不支撑结论**时，模型仍可能编（次因）。
> **filter 不是万能 → 但 critic 也不是，且 critic 连这条路径都覆盖不到。**
>
> —— `spike-report-v11-critic-phase2.md` §3.5

**该残留的精确形态**：

| 项 | 内容 |
|---|---|
| 触发条件 | **过滤后保留的 chunk 本身**（主题正确）内部不包含该结论的依据 |
| 表现 | 模型仍为该结论挂上该 chunk 的 `[n]` 编号 |
| 为什么 filter 治不了 | filter 只判断"这个 chunk 属不属于该主题"，**不判断"这句话是否被这个 chunk 支撑"** |
| 为什么 V1.1 不做 | 逐句配对判断需要语义理解（即 critic），而 critic 在 `kb_qa` 路径无 draft 可审；改造成本超出 V1.1 范围 |

### 4.1 V1.2 立项时 critic 的重新定义（**范围已缩小**）

> **从"泛泛的审查者"缩小为「草稿/正文与片段逐句配对审查（`troubleshooting` 路径先行）」。**

立项时赌注**直接对着 §4 这条残留写**，而不是对着"引用越界"这个笼统概念写：

| 建议赌注（V1.2 预置，非本迭代承诺） | 口径 |
|---|---|
| CB1 | `troubleshooting` 路径上"正确片段但内部不支撑"的越界句 = 0 |
| CB2 | 该路径 Recall / A3b 不降 |
| CB3 | 超时重分配后墙钟 ≤ 60000ms（见 §6 附注） |

> **为什么"troubleshooting 路径先行"而非全路径**：该路径有 `draft_answer`（critic 的唯一可用输入），
> `kb_qa` 要让 critic 可用必须先改造成"先出草稿再审查"，属结构性变更，不与本次同做。
> **kb_qa 的残留 1/15 在 V1.2 之前只能接受并如实记录。**

## 5. 赌注（防自欺三关下的预注册，详见 delta PRD §2）

本 ADR 只引用数字权威（delta PRD），不重复定义：

| 赌注 | 一句话 |
|---|---|
| **FB1** | 诱饵集越界流出 ≤ 基线 10%（21→≤2；**3 轮取均值**，单次 1 只算点估计） |
| **FB2** | 主集 Recall@5 on/off 差 = 0 **且** MRR ≥ 基线（**不许拿诱饵集涨抵主集跌**） |
| **FB3** | 延迟按配对法判定（见 §5.1）；达不到即"影响不可判定，按零声明处理" |
| **FB4** | 误杀回归固化：v1/v2 失败形态 + `q029` 阈值边界（1.5 必杀）作永久哨兵 |

### 5.1 FB3 的测量方法（裁决 3：换方法，不许各报裸 P95 比大小）

**原方法的问题**：n=15 时 P50 +594ms 而 P95 −1548ms，**方向打架** ——
说明测到的是模型时延噪声，不是过滤器的真实影响（filter 是纯计算，理论增量 ≈0）。

**新方法（预注册，先写死再跑）**：

```
30 题 × 3 轮，on/off **配对**（同题相邻跑，抵消账号/时段漂移）
统计：逐题配对差值的均值 ± 95% CI（bootstrap，10000 次重采样）
```

**达标线（预注册，事后不许改）**：

> **配对差值均值 ≤ +500ms 且 P50/P95 方向一致**

达不到 → 如实写 **"延迟影响不可判定，按零声明处理"**（即不宣称"零劣化"，也不宣称"劣化"）。

## 6. 附注：runbook 素材（裁决：把自己的错写成教训）

### 6.1 "调 LLM 的节点 ≠ 有超时的节点"

**事故**：SPIKE 首版 `s3_budget.py` 算出节点超时总和 **53000ms**，
而文档（`agent-workflow.md:205` / `计划书:327`）写 **59000ms**。
我一度怀疑是"文档↔代码漂移"。

**真相**：**是我算错。** 脚本只统计了 5 个"会调 LLM 的节点"，
**漏掉 `retrieval`（它不调 LLM，但有 `T_RETRIEVAL=6000ms` 超时）**。

**教训**：

| 约束 | 统计口径 | 易错点 |
|---|---|---|
| LLM 额度 `MAX_LLM_CALLS` | 只数**会调 LLM 的节点** | — |
| **超时总和 ≤ 墙钟** | **所有节点都算**（含纯代码节点） | **容易漏掉 retrieval 这类"不调模型但占时间"的节点** |

**推论**：`T_*` 在代码里没有对应常量（只在文档），
未来若把超时落代码，**建议用单一常量表驱动，且与 `agent-workflow.md` §5.1 双向校验**。

### 6.2 参数过拟合本语料（**已知限制，必须对外写明**）

> **`min_consistency = 1.0` 是在 5 篇语料 / 35 题上扫出来的。**
> **参数过拟合于本语料是事实，不是指控。**

**已知限制原文**（README / 报告 / 简历如需提及参数，必须带上这句）：

> 过滤参数以 5 篇语料 / 35 题标定，**新语料泛化未验证**，
> 上线新文档集前**须重扫阈值**（`scripts/spike_v11/s5b_threshold_scan.py`）。

**为什么必须写**：阈值扫描显示 1.0 与 1.5 之间只差一道边界（`q029` 被误杀），
**这个边界的宽窄完全取决于语料**。换个文档集，1.0 可能过严也可能过松。
不写这句，将来 Recall 崩了没人知道为什么。

### 6.3 BUD-3（checker 与 critic 互斥）的否决 — 保留教训

原方案"checker 已调用则跳过 critic"，理由是"避免重复审查"。
**代码反证**（`evidence.py:101/:104`）：

```python
supported = bool(kept) and not invalid
suspect = (not supported) or has_strong_claim(draft)   # ← 存疑才调 checker
```

**checker 被调用 = 草稿最可疑** → 互斥方案等于"在最可疑处撤审查"。
**教训：任何"跳过/互斥/降级"类优化，必须先读触发条件，不能凭"看起来重复"就砍。**

### 6.4 评测接线双份：越界降了，但审计字段是 None

**事故**（V1.1 评测首轮）：FB1 显示越界从 8.7 降到 0.7（看起来达标），
但逐题明细里 `filtered_out = 0`、`filter_reason = None` ——
**审计字段说"没过滤"，越界数字说"过滤了"**。两者矛盾。

**根因**：过滤被接在了**两个地方**：

| 位置 | 谁在调 | 是否执行 |
|---|---|---|
| 评测脚本的 `retrieve_fn` 外层 | 脚本自己包了一层 `filter_by_topic` | ✅ 执行（所以越界降了） |
| `retrieval` 节点内部（生产接线） | 按 `cfg["topic_filter_enabled"]` 判断 | ❌ **没执行** |

**为什么节点内没执行**：`run_turn` 内部调用 `get_config()`，
**不接收外部传入的 cfg**；而 `get_config()` 带 `@lru_cache`。
测试里 `cfg = dict(get_config()); cfg["topic_filter_enabled"]=True` 改的是**副本**，
节点拿到的仍是缓存里的 `False`。

**后果**（比"没过滤"更糟）：

- 数字看起来对，但**测的不是生产路径** —— 假如节点内接错了，评测照样绿；
- 审计字段（剔除明细）全空，**误杀无法复查**；
- on/off 两臂实际是"脚本外层开关" vs "节点内开关"，**不是同一件事的对照**。

**修正**（已实施）：

```python
# 评测脚本里必须先切环境变量 + 清缓存，让节点内真的读到 on
os.environ["TOPIC_FILTER_ENABLED"] = "true" if filter_on else "false"
app.config.get_config.cache_clear()
cfg = get_config()
assert bool(cfg["topic_filter_enabled"]) is filter_on   # 断言开关真的生效
```

并且 `retrieve_fn` **只做检索，不做过滤** —— 过滤唯一入口是节点内。

**教训（可复用）**：

> **凡"评测脚本包了一层、生产代码里也有一层"的地方，必须先断言"生产层真的执行了"。**
> 判据不是"结果变好了"，而是"**审计字段有值**"——
> 结果可能是被另一条路径改善的，而生产路径根本没跑。

这与 G7（纯函数测试不得充当装配点用例的替身）是同一类错误的变体：
**这次冒充装配点的是"评测脚本自己"**。
