## 0. ⚠️ 本 ADR 的核心结论已变化（v1 → v2）

**v1 的决策**：在 `final` 之前插入独立 critic 节点做逐句审查。

**v2 的实测发现**：**critic 覆盖不到缺陷所在路径**。

| 事实 | 证据 |
|---|---|
| 越界原型 m001（探针配置）走 `route=kb_qa` | `chk_route.py`：m001 原题/对照单轮/探针问题 → 全 `kb_qa, conf=1.0` |
| `kb_qa` 路径不产生 `draft_answer` | `prove_b.py`：`node_path=['router','retrieval','evidence','final']`，`evidence=method=skip` |
| critic 审 `draft` → 该路径**无输入可审** | `draft_answer` 只在 `troubleshoot.py:290/:327` 产生 |

→ **"要治的病住在 kb_qa，而 critic 只能治 troubleshooting"**。

**v2 的建议**：主药改为**检索主题一致性过滤**（`TOPIC_FILTER_ENABLED`），critic 降级为 V1.2 候选。
实测数据见 §8。

> **本文保留 v1 的全部论证**（§1–§7）—— 因为 critic 的工程可行性已被 SPIKE 证明，
> 且若 V1.2 决定做，这些论证仍然有效。**但"谁是主药"已由数据改写。**

## 1. 决策（v1，critic 部分）

在 **`final` 节点之前**插入一个**独立的 critic 节点**，对"结论句 × 其声明的片段原文"做**逐句配对审查**，并按其裁决执行三态处置。

**这是拓扑选择，不是实现细节。** 备选方案与否定理由见 §2。

### 1.1 图位置（SPIKE 实测修正，v1.1-2）

```
原（v1.1-1，错误）：
  final ──► critic ──► END

现（SPIKE 项 3 实测修正）：
  evidence ──► critic ──► final ──► END        （条件边：route=troubleshooting 或 超长）
  evidence ──────────────► final ──► END        （其余情况绕过 critic）
```

**为什么必须在 `final` 之前**（`reserved_for_final=1` 不变量）：

| 排位 | LLM 额度 | 后果 |
|---|---|---|
| critic 在 final **之后** | troubleshoot 最坏已用 5 次，final 消耗预留的那 1 次 → critic 无额度可拿 | ❌ 必然被抢占，critic 形同不存在 |
| critic 在 final **之前** | 非 final 可用额度 = `6 - 1 = 5`；router+rewrite+troubleshoot+checker+critic = **5** | ✅ 恰好用完，final 仍保有预留的 1 次 |

> **`reserved_for_final` 的语义是"final 永不被抢"**（PRD FR-36 / A6）。
> 排在 final 之后的节点**天然拿不到预留额度** —— 这是该不变量的直接推论。
>
> ⚠️ 代价：critic 若被判 `unsupported` 需要剥离句子，`final` **不能再基于被剥离的原文重新生成**
> （它已在 critic 之后）。所以 critic 的处置作用于**`draft_answer`**
> （`troubleshoot` 产出的草稿）或 `final` 的直通路径输入，
> 而非"改写 final 已输出的流式文本"。
> **对 `final` 需调模型的场景**：critic 审查的是 `final` 将要使用的 `draft_answer`，
> 审查结果通过 state 传给 `final`（由 `final` 在 prompt 中排除被剥离的句子）。
>
> 若实测发现该路径不可行（例如 `final` 在流式场景无法重入），
> **回退方案 = BUD-1 提额到 7 并把 critic 排在 final 之后** —— 但那样流式 `delta`
> 已经在 critic 之前发给用户，剥离无法生效。**故仍优选前置。**

### 1.2 位置决策的直接影响

- `final` 的 prompt 需新增输入：`critic_verdicts`（被剥离的句子清单），用于排除。
- **流式路径的注意点**：`final` 的 `on_delta` 会逐块发出文本。
  若 critic 在 final 之前，则剥离发生在**生成之前**（作用于 draft），流式输出天然是干净的 —— **这是前置的额外好处**。

## 2. 备选方案对比

### 2.1 方案 A：独立审查者（本 ADR 选择）

```
critic 在 final 之前（见 §1.1）
evidence / troubleshoot ──► critic ──► final ──► END
```

critic 收到的是**草稿 + 其声明引用的片段**，在**全新上下文**里独立判断每句话是否被其引用的片段支撑；
处置结果通过 state 传给 `final`，使其在生成时排除被剥离的句子（流式路径也因而天然干净）。

### 2.2 方案 B：自审（同一节点内让模型重读自己的输出）

```
final（生成 + 自审一体化）──► END
```

在同一个 LLM 调用或同一段 prompt 里追加"现在检查你上面写的内容是否有依据"。

**否定理由（核心论证）**：

| 问题 | 说明 |
|---|---|
| **自证盲区** | 生成时的上下文包含完整的思考路径与措辞动机。模型倾向于**为自己的选择辩护**（"我写这句是因为片段里提到过 X"），即使 X 实际不在片段中。 |
| **注意力锚定** | 同一个上下文里，模型对"我刚写过的东西"的注意力权重高于"片段原文"。这正是越界产生的原因，自审无法跳出该分布。 |
| **prompt 纪律已被证伪** | `chat.py` 的规则 1（引用纪律）与规则 3（编号必须与主题匹配）**就是**一种"事前自审提示"。实测 5/5 采样仍有越界（`v3_residual_notes.md` 第 7–13 行）。**继续在同一个 prompt 里加规则，属于已被证伪的路径**。 |
| **无法逐句归因** | 自审拿不到"这句话 声明引用的是哪一条片段"的显式配对，只能整体判断"这份答案看起来靠不靠谱"。 |

> **关键论证**：越界的根因是**生成时的注意力**（模型在写结论时把自身知识带进来了）。
> 要检测它，必须让判断者处于**没有该注意力偏向的上下文**里。
> 这就是"生成与审查不共享上下文/提示词"的必要性 —— 不是洁癖，是**破自证盲区的手段**。

### 2.3 方案 C：规则层加强（扩大 `detect_citation_overreach` 的字典/权重）

**否定理由**：

- 现有检测器基于"技术标识符是否出现在片段原文"，**当前已经 0/5 干净** —— 说明它抓得到信号，
  问题在于它**只观测不阻断**。
- 但直接把"检测到就删引用"作为处置，会发生**误删**：一句合法结论可能因为
  同义改写（片段写"存活探针"，答案写"livenessProbe"）被判越界。
  实测 `a3b_user_review_v3.md` q001 的判定备注就写着"（livenessProbe）是同义注记，未引入片段外事实"——
  **这种句不该被删**。
- 规则层无法区分"同义注记"与"引入片段外事实"，需要语义判断 → 需要模型。

**结论**：规则层保留为**廉价前置过滤器**（critic 只审规则层命中的句子，降低 critic 输入量），
但**不能作为唯一处置层**。

## 3. 输入契约（数据最小化，防越界扩散）

### 3.1 critic 的输入**只允许**这两项

| 字段 | 内容 |
|---|---|
| `claim` | 单句结论（从 `final_text` 按句切分，仅取**含 `[n]` 标记的句子**） |
| `pairs` | 该句声明引用的编号 + **对应片段的完整原文** |

```json
{
  "claim": "启动慢的应用应改用 startupProbe 提供启动宽限期[1]。",
  "pairs": [
    {"index": 1, "doc_title": "k8s-pod-troubleshooting",
     "source": "常见错误是把耗时的启动检查放进 livenessProbe，导致应用还没启动完就被反复重启。启动慢的应用应使用 startupProbe 保护。"}
  ]
}
```

### 3.2 禁止注入的内容（硬约束）

| 禁止项 | 理由 |
|---|---|
| `question`（用户原始问题） | **不是必需**，且会引入"这答案整体是否切题"的干扰。critic 的职责是"这句话是否被该片段支撑"，不是"这答案好不好" |
| `history`（对话历史） | 同上，且会带来指代消解问题 |
| 生成过程的中间产物（`draft_answer`、`check_result`、router 推理） | **这是破自证盲区的关键** —— critic 一旦看到"生成时怎么想的"，就重新陷入方案 B 的锚定 |
| 其余片段的全文 | 只给**该句声明的**那几条。给全量会让 critic 做"帮它找依据"而不是"核对声明" |

> **实现要求**：critic 应为**独立的一次 LLM 调用**，prompt 里**不包含**上述任何字段。
> 该约束须有测试断言（`test_critic_input_minimization`）。

### 3.1.1 切分粒度：必须复用 `_SENTENCE_SPLIT`（硬约束，不留给 SPIKE 选）

**问题**：B1 的**测量口径**（`detect_citation_overreach` 的切句）与**处置口径**（critic 的 claim 切分）
若不一致，两套数字**不可比** —— 检测器扫的句子和 critic 审的句子不是同一个集合，
"detector 报 0 命中"就可能只因为在 critic 的切分下那句话被拆/并成了别的形态。

**硬约束**：

| 项 | 规定 |
|---|---|
| 单一来源 | critic 的 claim 切分**必须**复用 `chat.py:281` 的 `_SENTENCE_SPLIT = re.compile(r"(?<=[。！？\n])")` |
| 禁止 | **不得**在 critic 模块内重新定义切句正则、不得引入第三方分句库 |
| 断言 | 新增 `test_critic_claim_split_matches_detector`：对同一段文本，critic 的 claim 列表与 detector 的 `_SENTENCE_SPLIT.split` 结果**逐项相等**（集合与顺序均需一致） |

**为什么升格为硬约束而非未决项**：这是**测量有效性**的前提，不是实现偏好。
若两者切分不同，B1 的"0 命中"随时可能是口径错位造成的假绿 —— 属于"评测被自己机制 gamed"的另一条路径
（与 §4.2 的撤标盲区并列）。

> `_SENTENCE_SPLIT` 的当前唯一使用点是 `detect_citation_overreach`（`chat.py:311`）。
> critic 引入后它变成**两个消费者共享的公共常量** —— 若将来修改该正则，
> 必须同时回归这两处（维护规则 1：改值后回读所有引用位置）。

### 3.3 为什么"只审含 `[n]` 的句子"

- 无 `[n]` 的句子**没有声明引用**，即使含片段外内容也不构成"引用越界"
  （PRD FR-18③ 允许标注"模型通用知识，无 KB 出处"）。
- 这样把 critic 输入量压到**答案中最小的关键子集**，直接服务于 §4 的预算约束。

## 4. 输出 Schema

### 4.1 严格 schema（JSON mode）

```json
{
  "verdicts": [
    {
      "claim_index": 0,
      "verdict": "supported",
      "reason": "结论与片段首句逐字对应"
    },
    {
      "claim_index": 1,
      "verdict": "unsupported",
      "reason": "片段来自《Linux 网络故障排查》，全文不含 livenessProbe 内容，无法支撑探针重启结论"
    },
    {
      "claim_index": 2,
      "verdict": "needs_downgrade_label",
      "reason": "片段提到 startupProbe 保护启动慢应用，但未给出具体参数值，参数建议属片段外"
    }
  ]
}
```

### 4.2 三态定义（**互斥且穷尽**）

| verdict | 语义 | 判定标准 |
|---|---|---|
| `supported` | 该片段**确实支撑**该结论 | 结论的事实要素能从片段原文直接读出（允许同义改写，如"存活探针"↔`livenessProbe`） |
| `unsupported` | 该片段**完全不支撑**该结论 | 片段主题与结论对象无关（如用《Linux 网络排查》支撑探针结论），或结论的核心事实在片段中不存在 |
| `needs_downgrade_label` | 结论**部分**有依据，但含片段外内容 | 结论主体有依据，但附带了片段未给出的**具体参数/数值/机制** |

> **三态而非二态的理由**：二态（支持/不支持）会在"主体对、细节超出"的情况下二选一错。
> 见 `a3b_user_review_v3.md` q001：结论是片段原句，括号里加了 `(livenessProbe)` 同义注记 ——
> 判 `unsupported` 会误删正确内容；判 `supported` 又放过了一个片段外的词。`needs_downgrade_label` 才是准确落点。

### 4.3 处置策略（全部动作进 trace，**禁止静默修改**）

| verdict | 处置 | 用户可见结果 |
|---|---|---|
| `supported` | **不改动** | 原样保留，含 `[n]` |
| `unsupported` | **剥离该句**（整句删除），同时移除该句独占的引用 | 该句不出现；若因此引用列表变空，走 `final` 的兜底归因（`final.py:262`） |
| `needs_downgrade_label` | **改标**：该句的 `[n]` 移除，句尾追加「（模型通用知识，无 KB 出处）」 | 内容保留、引用撤除，用户能看出"这不是文档里的" |

**三条硬规则**：

1. **禁止静默**：每次处置必须写入 `run_steps` 的 critic step（含 `claim` 摘要、`verdict`、`reason`、`action`），
   前端轨迹抽屉可见。
2. **禁止整段重写**：只允许"删除句 / 撤引用+追加标注"，**不允许**让 critic 改写语句内容
   （改写会引入新的、未经审查的文本，等于把审查者变成生成者）。
3. **剥离后必须复核非空**：若剥离导致 `final_text` 为空 → **放弃全部剥离**，回退原文并 `degraded=true`
   （宁可有越界，不可给用户空白答案）。

## 5. 与 `evidence.checker` 的职责边界（避免重复审查）

现有 `evidence` 节点的 checker LLM（`evidence.py:106-110`）也在判断"结论是否被片段支持"。必须划清：

| 维度 | `evidence.checker`（既有） | `critic`（新增） |
|---|---|---|
| 作用对象 | **整份 `draft_answer`** | **单句 claim × 其声明的片段**（配对） |
| 触发时机 | `final` **之前** | `final` **之后** |
| 触发条件 | draft 存在 且 (`not supported` 或 含强断言) | `route=troubleshooting` 或 超长答案（见 delta §3.1） |
| 输出粒度 | 布尔 `supported` + `method` | 每句一个 verdict + reason |
| 处置能力 | **无**（只把结果传给 final 做 prompt 提示） | **有**（三态处置，见 §4.3） |
| 失败影响 | 退回纯规则，不阻断 | 跳过 critic，`degraded=true`，**原样输出** |

**互补性论证**：checker 管"这份草稿整体靠不靠谱"（粗粒度、生成前），critic 管"每一句是否被它自己声明的片段支撑"（细粒度、生成后且可处置）。
**二者的重叠部分是"支持性判断"，但作用粒度与处置能力不同** —— 不构成重复。

### 5.1 ⚠️ 已作废的方案：checker 与 critic 互斥（delta 的 BUD-3）

**本节记录一次被否决的设计，防止后续重新提出。**

> **命名注意**：这里说的是 delta PRD §4.3 的**预算方案 BUD-3**（二者互斥），
> **不是** §2.3 的拓扑方案 C（规则层加强）。两套编号互不相关。

原 delta PRD §4.2 曾提出"BUD-3：critic 只在 `checker` 未调用时启用（二者互斥）"，
理由是"checker 已做过同类判断，边际收益低"。

**该理由错误。** 反证如下（代码原文）：

```python
# evidence.py:101
supported = bool(kept) and not invalid
# evidence.py:104
suspect = (not supported) or has_strong_claim(draft)   # ← 存疑才调 checker
```

`checker` 的**触发条件本身就是"草稿可疑"**：
- `not supported` = 没有有效引用，或存在被剔除的无效引用；
- `has_strong_claim(draft)` = 草稿含"根因是/一定是/必然是"类强断言。

所以 **`checker` 被调用 = 这份草稿最可疑**。互斥方案的实际效果是：

> **在最可疑的答案上取消逐句审查，在最干净的答案上保留逐句审查。方向完全反了。**

这与 ADR §2.3 自己的论证直接矛盾 —— 那里已经说明"规则层无法区分同义注记与片段外事实，
需要语义判断"，而 checker 恰恰是**整份粒度、且无处置能力**的语义判断。
"被 checker 放行"不等于"逐句都干净"，因为 checker 只输出一个布尔 `supported`（`evidence.py:121-126`）。

**结论**：BUD-3 **降级为"待实测裁决的候选"**，不得凭直觉决定。裁决方式见 §7 未决事项 #2。

## 6. 后果

### 6.1 正面

- 越界从"仅可观测"变为"可处置"，直接对应 `v3_residual_notes.md` 残留 1 的收口要求。
- 审查者上下文隔离 → 破自证盲区，这是 prompt 层纪律（已被 5/5 采样证伪）做不到的。
- 全动作进 trace → 可回归、可复核，不是黑盒。

### 6.2 负面（必须承认）

| 负面 | 量级 | 缓解 |
|---|---|---|
| **多一次 LLM 调用** | troubleshoot 最坏路径 5→6，**顶满 `MAX_LLM_CALLS`** | 只审含 `[n]` 的句子；SPIKE 定预算方案 |
| **多一次网络往返** | troubleshoot P95 会增加（赌注 B4 保证 ≤25s） | 该路径 P95 阈值 25s，余量比 kb_qa 的 8s 宽 |
| **可能误删正确内容** | 取决于 critic 准确率 | 三态而非二态；剥离后非空校验；`needs_downgrade_label` 保留内容 |
| **「引错编号」会被判 unsupported** | 一句**内容正确**的结论若把 `[2]` 误标成 `[3]`，critic 只看声明的那条片段（`[3]`）→ 判 `unsupported` → **正确内容被剥离** | **这是输入最小化的必然代价，不修。** 理由见下 |
| **引入新的失败模式** | critic 超时/格式错误 | 失败即跳过 + `degraded=true`，**绝不阻断答案**（与 checker 同策略） |

#### 6.2.1 为什么"引错编号"这个代价不能修

修它的唯一办法是让 critic 看到**全量片段**（"这条结论到底该配哪一条？"）——
但那正是 §3.2 明令禁止的：一旦给了全量片段，critic 就从"核对声明"退化成"帮生成者找依据"，
**方案 A 的根基（输入最小化破自证盲区）被摧毁**。

**处置（不修，但要可见）**：

- critic 的 `reason` 中输出 **`疑似错位引用`** 提示（当片段主题与 claim 明显不符、
  但其他片段可能支持时），写入 `run_steps` 的 critic step，**前端轨迹抽屉可见**；
- **禁止自动改配**（自动把 `[3]` 改成 `[2]`）—— 那需要 critic 看全量并与生成者争夺"该引哪条"的判断权，
  属越界，且会引入新的未审查决策。

### 6.3 明确不承诺

- **不承诺 overreach 归零是永久性的**。B1a/B1b 只保证"本次评测的 35 题 + 专项集上 0 处"。
  模型行为会漂移，**该赌注需在后续每次评测复验**。
- **不承诺"机器口径 0 命中"就等于收口**。detector 只扫含 `[n]` 的句子，而 critic 的处置之一
  恰是撤掉 `[n]` —— **撤标即隐身**。B1a 单独不构成收口证明，必须配 B1b 人工复核
  （delta PRD §2.1）。
- **不承诺替代人工复核**。critic 是机器审查者，A3b 的人工抽样（≥90%）**仍然保留**。

## 8. 【v2 新增】主药裁决：检索主题一致性过滤（TOPIC_FILTER）

### 8.1 为什么换药：critic 覆盖不到发病部位

| 维度 | critic | filter |
|---|---|---|
| 作用位置 | 生成后（`final` 之前） | **检索后**（retrieval 之后、evidence 之前） |
| 治疗对象 | 模型挑错编号（**次因**） | 无关文档进入引用池（**主因**） |
| 路径覆盖 | **仅 `troubleshooting`** | **全路径**（kb_qa + troubleshooting） |
| 缺陷原型 m001 是否覆盖 | ❌ 否（走 kb_qa，无 draft） | ✅ 是 |

`v3_residual_notes.md:33-36` 的因果链原话：

> 根因定位（实测）：`m001` 的检索集（5 条）稳定混入 `linux-network-troubleshooting`
> 与 `nginx-502-upstream` 等**与探针无关**的文档；rewrite 本身**是生效的**……
> 问题是改写后的检索仍带回无关文档，而模型没能稳定守住"编号必须与主题匹配"。

→ **主因在检索层，次因在生成层。critic 治次因且覆盖不到主犯路径。**

### 8.2 方案设计（确定性规则，零 LLM）

**输入**：`query` 或 `rewritten_query`、检索返回的 `chunks`
**输出**：过滤后的 `chunks` + 诊断信息（被剔除项及理由）

**锚点提取优先级**（顺序错了会误杀，见 §8.3 调参过程）：

| 优先级 | 类型 | 例 |
|---|---|---|
| ① | 错误码 / 错误短语 | `Exit Code 137`、`Connection refused`、`Error 1040`、`Too many connections`、`Lock wait timeout` |
| ② | 技术标识符 | `livenessProbe`、`proxy_read_timeout`、`initialDelaySeconds` |
| ③ | 领域词表（含同义展开） | "探针" → `探针/probe/liveness/readiness/startup/健康检查` |
| ④ | 中文实义词兜底（**过滤疑问短语**） | 仅当 ①②③ 全空时启用 |

**打分规则**：

| 命中位置 | 权重 | 理由 |
|---|---|---|
| `heading_path` | 3.0 | 标题即主题，最强信号 |
| 正文前 1/3 | 1.0 | 开篇即主题 |
| 正文后 2/3 | 0.3 | 可能只是顺带提及 |
| **强信号豁免** | **3.0 + 命中数** | 错误码/技术标识（含数字、`probe`、`refused` 等）**任何位置都算强相关** |

**阈值**：`min_consistency=1.0`；**全被剔除时兜底保留最高分 chunk**（避免把答案饿死）。

### 8.3 调参过程（三版，过程必须留痕）

| 版本 | 关键改动 | Recall@5 | MRR@5 | 判定 |
|---|---|---|---|---|
| v1 | 只切中文词（2~5 字） | **0.7407** ❌ | 0.7222 | 误杀 5 题（`q002/q007/q011/q012/q013`） |
| v2 | 优先提取错误码/错误短语 | 0.7407 ❌ | 0.7222 | 锚点对了，但打分仍误杀 |
| **v3** | **强信号豁免**（关键修正） | **0.9259** ✅ | **0.8704** ✅ | **Recall ±0，MRR +0.0975** |

**v1 的根因**（`diag_loss.py` 实测）：疑问短语被当成锚点 ——
`"Exit Code 137 一般代表什么？"` → 锚点 = `['一般代表']`；
真正的 `Exit Code 137` **完全没提取到**。

**v2 后仍误杀的原因**（单 chunk 复现）：

```python
anchors = ['exit code 137']
chunk.content = '...表现为 Exit Code 137。'   # 命中在正文后 2/3
→ score = 0.3  < 阈值 1.0  → 被剔除
```

**这是设计缺陷**：错误码在运维文档里是**唯一标识**，不会作为无关内容出现。
"一律按位置给 0.3 权重"把它误判成"顺带提及"。
→ 新增 `_STRONG_ANCHOR_MARKERS` 豁免，命中即满分。

### 8.4 实测效果（三臂对照，15 run/臂）

| 臂 | 配置 | 有越界 run | 越界总数 | Recall@5 | MRR@5 | P50 | P95 |
|---|---|---|---|---|---|---|---|
| **A** | 基线 | **10/15 (67%)** | **21** | 0.9259 | 0.7728 | 6781ms | 9875ms |
| **B** | critic on | **结构无效**（kb_qa 无 draft） | — | — | — | — | — |
| **C** | **filter on** | **1/15 (7%)** | **1** | **0.9259** | **0.8704** | 7375ms | 8327ms |

**越界降 95%（21→1）；Recall 零损失；MRR 反升；零 LLM 调用；零超时增量。**

> **C 臂残留 1 处必须记录**：`q001` 第 5 轮。说明过滤解决"污染进入引用池"（主因），
> 但**正确片段内部本身不支撑结论**时，模型仍可能编（次因）。
> **filter 不是万能 → 但 critic 也不是，且 critic 连这条路径都覆盖不到。**

### 8.5 成本对比（结构性差异）

| 约束 | critic | filter |
|---|---|---|
| LLM 额度 | +1 次（非 final 额度 5→刚好用完，**零余量**） | **+0** |
| 超时总和 | +6000ms → **65000ms > 60000ms 墙钟**（必须砍其他节点） | **+0ms** |
| 延迟 | +1 次往返（实测 flash median 1625ms） | 纯字符串匹配，P95 实测未劣化 |
| 可回归性 | 依赖模型随机性 | **确定性，结果可复现** |
| 依赖 | 需要可用模型、预算、迁移、前端改造 | **无外部依赖** |

### 8.6 阈值扫描（未决事项 #8 已实测裁决）

**命令**：35 题主集，扫 `min_consistency ∈ {0.0, 0.3, 0.6, 1.0, 1.5, 2.0, 3.0}`

| 阈值 | Recall@5 | MRR@5 | 检索集均值 | 保留率 | 丢失题 |
|---|---|---|---|---|---|
| 0.0（=不过滤） | 0.9259 | 0.7728 | 4.44 | 100% | 0 |
| 0.3 | 0.9259 | **0.8704** | 1.89 | 42.5% | 0 |
| 0.6 | 0.9259 | **0.8704** | 1.89 | 42.5% | 0 |
| **1.0（选用）** | **0.9259** | **0.8704** | **1.74** | **39.2%** | **0** |
| 1.5 | 0.9259 | 0.8333 | 1.63 | 36.7% | **1**（`q029`） |
| 2.0 | 0.9259 | 0.8333 | 1.63 | 36.7% | 1 |
| 3.0 | 0.9259 | 0.8333 | 1.56 | 35.0% | 1 |

**裁决：`min_consistency = 1.0`**

- **1.0 是拐点**：MRR 达最高（0.8704），再往上（1.5+）开始误杀 `q029` 且 MRR 反而下降
- **0.3/0.6 的 MRR 与 1.0 相同**，但检索集更大（1.89 vs 1.74）→ 同等效果下更精简优选 1.0
- **`q029` 为何在 1.5 被误杀**：它就是 v3 复核里"角标 vs 清单展示"那条题
  （`a3b_user_review_v3.md` §2），gold 片段与 query 的主题词重合度低 ——
  **这个案例说明阈值不能盲目调高**，1.0 已接近该题的可容忍边界。
- **保留率 39.2%**：过滤后平均只剩 1.74/4.44 个 chunk。
  这是**有意为之**（污染项被剔除），但**必须记住：检索集变小意味着答案可引用的依据变少**，
  B2 的 Recall 赌注就是为防这件事。

> ⚠️ 0.3 与 1.0 的 MRR 相同但保留率不同，说明**大部分被剔除的 chunk 集中在 0.3~1.0 区间**
> （即"只有正文后段弱命中"的那类）。选 1.0 更严格，对 overreach 的抑制也更彻底。

### 8.7 filter 不是万能的（诚实边界）

三臂对照里 C 臂仍有 **1/15 残留**（`q001` 第 5 轮）。必须说清它治不了什么：

| 能治 | 治不了 |
|---|---|
| 无关文档混进引用池（**主因**） | 正确片段**内部本身**不支撑该结论时，模型仍会编（**次因**） |
| 编号挂到主题不符的文档上 | 编号挂对文档、但结论超出了该片段的表述范围 |
| 检索层面的污染 | 生成层面的"合理发挥" |

**这恰恰是 critic 理论上该补的洞** —— 但 critic 覆盖不到 `kb_qa` 路径（§8.1），
所以在 V1.1 范围内，这个残留**只能接受并如实记录**，不能宣称"已根治"。

> README / pitch / 简历中的表述底线：
> 可写"引用越界流出降低 95%（21→1，三臂对照实测）"，
> **不可写"引用越界已根治"**。

### 8.8 建议（交外部裁定）

**V1.1 主药 = filter；critic 推 V1.2。**

理由按权重：

1. **覆盖**：filter 全路径，critic 只覆盖非缺陷路径 —— 覆盖不到病灶的方案不值得先做。
2. **数据**：filter 实测 −95% 且检索指标双优；critic 对 kb_qa **零覆盖**、无实测收益。
3. **成本**：filter 零预算；critic 撞墙钟 5000ms + 额度零余量。
4. **可回归**：filter 确定性；critic 有随机性。

**若外部裁定"两者都要"**，必须同时满足（已量化）：

- 超时重分配：`rewrite` 5000→3000、`checker` 10000→8000、`troubleshoot` 15000→12000
  → `critic 6000` 时总计 58000ms ✅（BUD-1d）
- critic 必须在 `final` 之前（`reserved_for_final` 不变量）
